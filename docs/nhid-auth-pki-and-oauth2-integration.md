# NHID-Auth v2 — PKI for Voice Vendors & OAuth2/OIDC Integration Guide

**Version:** 1.0 · **Spec baseline:** NHID-Clinical v1.3 + NHID-Auth v2 · **Status:** Reference architecture + production-migration guidance

> NHID-Clinical is a voluntary open proposal, CC BY 4.0, not an accredited standard or
> regulatory requirement. This document describes the **reference implementation** of
> NHID-Auth v2 as it exists in `src/agent_identity.py` today, and separately lays out
> **forward-looking production recommendations** that are not yet implemented. Each section
> is labeled accordingly.

## Part 1 — Public Key Infrastructure for Voice Vendors

### 1.1 What NHID-Auth v2 provides today (reference implementation)

From `src/agent_identity.py`:

- **Algorithm:** Ed25519 (Curve25519, twisted Edwards) — 32-byte public keys, 64-byte signatures. Chosen for small key size, fast verification, and resistance to common side-channel issues relative to RSA.
- **Core objects:** `Delegation` (provider NPI + agent ID + agent public key + scope + TTL + call-SID binding), `AgentPassport` (delegation + provider signature + agent co-signature), `VerificationResult`.
- **Delegation chain rules:** maximum 3 hops (Provider → Vendor → Sub-vendor → Agent), monotonic scope narrowing only, NPI-anchored, call-SID nonce bound, revocation is permanent.
- **Storage:** revocation state is **in-memory** in the reference implementation. This is explicitly a reference/demo limitation, not a production design.

This is a working trust *primitive*, not a deployed trust *infrastructure*. The rest of this section addresses what changes between the reference implementation and a production deployment serving real provider organizations and real voice vendors.

### 1.2 Trust anchors: provider keys vs. vendor keys

Two distinct key materials exist in every NHID-Auth flow, and they answer different questions:

| Key material | Answers the question | Held by |
| :-- | :-- | :-- |
| **Provider root key** | "Is this delegation authorized by the provider organization whose NPI is named in it?" | The provider organization (or a custodian acting for them — see §1.4) |
| **Agent key** | "Is the entity presenting this passport on the call actually the agent the delegation names?" | The AI voice vendor's runtime, one keypair per agent instance (minimum: per provider-tenant) |

The provider key is the trust anchor. Everything downstream — vendor platforms, sub-vendors, individual agent instances — derives its authority from a signature chain rooted at a provider key tied to a real NPI. This is why NPI anchoring is a hard requirement in the delegation chain rules (§4.4 of the Master Knowledge Archive) rather than a convenience field.

### 1.3 Who issues keys: the provider, or the vendor?

**The agent's own keypair is generated by whoever runs the agent runtime — almost always the vendor.** The provider does not (and should not) generate or hold the vendor's signing key; that would require the provider to operate vendor infrastructure. What the provider *does* do is **sign a delegation that names the vendor's agent public key**, which is the cryptographic equivalent of saying "I, the provider, authorize the holder of this specific public key to act on my behalf, within this scope, for this call."

This separation is deliberate:

- The provider never needs to see or manage the vendor's private key.
- The vendor never needs the provider's private key — only the provider's public key, to verify nothing (verification happens payer-side) and to receive a delegation signed by it.
- Compromise of one party's key does not compromise the other's signing capability — only the validity of *delegations issued between* them.

### 1.4 Generating and rotating agent keypairs

**Reference behavior today:** `AgentIdentityManager.generate_agent_keys()` generates an Ed25519 keypair in-process, with no persistence or rotation logic — it's designed for the demo/example flow (`examples/issue_and_verify.py`), not a fleet of long-running agents.

**Production recommendation:**

1. Generate agent keypairs inside a KMS or HSM boundary (AWS KMS asymmetric keys with `ECC_NIST_P256` or a dedicated Ed25519-capable provider, GCP Cloud KMS, HashiCorp Vault Transit) so the private key material never exists outside the boundary in plaintext.
2. One keypair per **agent instance per provider-tenant**, not one keypair shared across all of a vendor's customers (see §1.6).
3. Rotate on a fixed window — recommend **30–90 days** for routine rotation, immediate rotation on any suspected compromise. Rotation means: generate a new keypair, obtain a fresh provider-signed delegation for the new public key, and let the old delegation's TTL lapse naturally (don't need to revoke if the TTL is already short — see §1.9).
4. Because a delegation already carries its own TTL (recommended: bounded to call-duration scale or, for longer-lived delegations covering many calls, no more than a few hours), key rotation and delegation rotation can be the same operational event.

### 1.5 Multi-tenant vendor platforms: isolating keys per customer

A vendor platform serving many provider organizations from one codebase must not let one customer's compromise expose another's call authorization. Concretely:

- **Do not** use a single agent keypair across all provider tenants "for simplicity." A leaked key would let an attacker forge delegations claiming to act for *any* provider the vendor serves.
- **Do** provision a distinct keypair (or distinct KMS key alias) per provider tenant, even if the underlying agent *software* is identical across tenants. The identity that matters cryptographically is "this specific delegation, for this specific provider NPI," not "this vendor's product."
- Store the mapping of `(provider_tenant_id → key alias → current public key)` in the vendor's own control plane, separate from the call-handling runtime, so a compromised call-handling process cannot read other tenants' key material.

### 1.6 Sub-vendors and delegated platforms

NHID-Auth v2's delegation chain supports up to 3 hops specifically to accommodate the common real-world pattern of *vendor platforms built on top of other vendor platforms* (e.g., a clinic-facing SaaS product that itself runs on a white-labeled voice AI platform):

```
Provider (NPI holder)
   │  signs delegation scoped to "claims_inquiry"
   ▼
Vendor platform (e.g., the SaaS company the provider contracted with)
   │  signs a narrower delegation — same or smaller scope, never larger
   ▼
Sub-vendor / underlying voice AI platform
   │  signs the final delegation to the actual agent keypair
   ▼
Agent instance (the thing that's actually on the phone)
```

**Monotonic scope narrowing is the safety property that makes this chain trustworthy without a central registry.** Each hop can only restrict what the next hop is allowed to do, never expand it — so even if hop 2 (the SaaS company) is compromised, it cannot grant itself authority the provider never granted. The reference implementation enforces this with `ERR_CHAIN_NARROWING` and caps depth with `ERR_CHAIN_TOO_LONG`.

If a deployment needs a 4th hop (e.g., provider → reseller → platform → sub-platform → agent), that is a sign the architecture should move to registry-based trust discovery (§1.10) rather than stretching the hop limit, since per-hop signature verification cost and revocation-propagation complexity both grow with chain depth.

### 1.7 Modeling certificate-like trust without full X.509

Full X.509 PKI (CA hierarchies, CRLs, OCSP, ASN.1 certificate profiles) is more machinery than this trust problem currently needs, for two reasons: the trust graph is shallow (≤3 hops) and the parties are typically already in a contractual relationship (provider ↔ vendor) before any key exchange happens. NHID-Auth v2 instead uses what is effectively a **lightweight, application-specific certificate**: a signed JSON object (the `Delegation`) with the fields a certificate would carry (subject = agent public key, issuer = provider, validity window, scope), without ASN.1 encoding or a CA hierarchy.

This is an appropriate simplification **today**, while NHID-Clinical is a reference/pilot-stage proposal with a small number of participating organizations who can exchange public keys directly. It stops being appropriate once the participant count grows past what direct, bilateral key exchange can support — that's the trigger for moving to §1.8/§1.10.

### 1.8 JWKS-style discovery vs. static key exchange

| Approach | When it's right | Tradeoff |
| :-- | :-- | :-- |
| **Static exchange** (provider emails/uploads a public key once, vendor stores it) | Small number of relationships, pilot/early-adopter stage — matches NHID-Clinical's current status | Manual, doesn't scale past a handful of counterparties, no built-in rotation signaling |
| **JWKS endpoint** (`https://provider.example.org/.well-known/nhid-jwks.json` serving a standard JWK Set) | Once a provider organization has more than a few vendor relationships, or wants self-service rotation | Standard, well-understood (same pattern OIDC providers use for signing keys), but requires the provider to operate and secure a public endpoint |
| **Registry-backed resolution** (a shared, neutral directory mapping NPI → current public key / JWKS URL) | Production, multi-payer, multi-vendor ecosystem — the eventual target state | Requires a trusted registry operator and a registration/verification process for who may claim a given NPI; this is the most infrastructure-heavy option and does not exist yet for NHID-Clinical |
| **Signed metadata bundles** (a provider publishes a single signed JSON document containing its public key + NPI + supported scopes, distributed out-of-band or via the registry) | Bridges static exchange and registry models — useful during the transition period | Still requires *some* distribution channel and a way to verify the bundle's own signature came from a trusted source (chicken-and-egg on first contact, same as any first-key-exchange problem) |

**Current recommendation for pilot participants:** static exchange now, with delegation objects structured so that migrating to JWKS later only changes *how the public key is fetched*, not the shape of the delegation or passport objects themselves.

### 1.9 Revocation list strategy

**Reference implementation:** in-memory revocation set inside `AgentIdentityManager`; `revoke_agent()` and `revoke_delegation()` are permanent and irreversible by design, but state does not survive a process restart.

**Production recommendation:**

- Persist revocations in a durable, low-latency store (e.g., DynamoDB, keyed by `agent_id` and by `delegation_id`), checked synchronously on every passport verification — not a periodically-refreshed CRL pulled on an interval, since the whole point of per-call verification is catching a revocation immediately.
- Because delegations are already short-lived (recommend bounding TTL to the scale of a single call or a small batch of calls), the revocation list never needs to grow unboundedly — entries can be pruned once their underlying delegation's TTL has already elapsed, since an expired delegation fails verification on `ERR_EXPIRED` regardless of revocation status.
- Treat revocation propagation latency as a security SLA, not a performance nice-to-have: target sub-second visibility of a revocation to the verifying (payer) side.

### 1.10 Key rotation windows — summary

| Material | Recommended rotation | Trigger for early rotation |
| :-- | :-- | :-- |
| Agent keypair | 30–90 days | Suspected compromise, vendor staff turnover with key access, platform migration |
| Delegation (per-key authorization) | Call-duration scale, or hours for batch authorizations | Scope change, provider relationship change |
| Provider root key | Annually, or per provider's own key-management policy | Suspected compromise, organizational change (e.g., NPI reassignment) |

### 1.11 Operational security for HSM/KMS-backed signing

- Signing operations (provider delegation signatures, agent co-signatures) should happen inside the KMS/HSM boundary — the application code calls a `sign()` API and never holds raw private key bytes.
- Separate IAM/access-control roles for "can request a signature" vs. "can manage/rotate the key" — a compromised call-handling service should be able to *use* the key, not *export or delete* it.
- Log every signing operation (who/what requested it, for which delegation) as part of the same audit trail that ATR-01 requires for call events — a signature is itself an auditable action.
- Set a hard cap on signing rate per key (a sudden spike in delegation-signing requests for one provider key is itself a compromise indicator).

### 1.12 What a payer must retain to verify a disputed call later

To resolve a dispute ("was this call actually authorized by the provider it claimed to represent?") months after the fact, retain at minimum:

1. The full `AgentPassport` presented on the call (delegation + provider signature + agent co-signature) — not just a "verified: true" boolean.
2. The provider public key (or JWKS reference + the JWKS document as it existed at call time, since keys rotate) used to verify it.
3. The verification result and timestamp, including which scope was checked against which requested action.
4. The call-SID the credential was bound to, and confirmation it matched the actual call.
5. The full FHIR `AuditEvent` Bundle for the call (see the [FHIR AuditEvent standardization guide](fhir-auditevent-standardization-for-ai-agents.md)) — this is the behavioral evidence (disclosure, PHI gating, escalation) that sits alongside the cryptographic evidence above. Cryptographic proof of *who* was authorized and behavioral proof of *what they actually did* are both required to resolve most real disputes.

Retention period should match the payer's existing audit-log retention policy for comparable administrative call records — this guide does not set a number, since that's a regulatory/contractual question outside NHID-Clinical's scope.

### 1.13 Binding keys to provider identity and NPI assertions

The binding is structural, not advisory: the `Delegation` dataclass carries `provider_npi` as a required field, validated by `^\d{10}$` (NPPES format), and that field is included in what the provider's signature covers. This means:

- You cannot have a validly-signed delegation that omits or alters the NPI without invalidating the provider's signature.
- Verification (`verify_passport`) returns the `provider_npi` in its result, so the payer-side caller can independently check it against their own provider directory (e.g., confirm the NPI is enrolled with them) — NHID-Auth proves the *delegation* is authentic; it deliberately does not assert that the NPI itself is a legitimate, active NPPES registration. That check belongs to the payer's existing provider-enrollment system, which is the authoritative source for "is this NPI real and in good standing."

### 1.14 Migrating from the reference model to production-grade trust infrastructure

Recommended sequence, each step independently shippable:

1. **Move revocation from in-memory to a persistent store** (§1.9) — no API change, pure durability fix.
2. **Move signing into KMS/HSM** (§1.11) — changes *where* `generate_agent_keys`/`sign_delegation` execute, not their external contract.
3. **Add per-tenant key isolation** for multi-tenant vendor platforms (§1.5) — primarily a vendor-side control-plane change.
4. **Introduce JWKS endpoints** for providers with more than a handful of vendor relationships (§1.8) — additive; static exchange continues to work for everyone else.
5. **Stand up (or join) a registry** for NPI → public-key/JWKS resolution once the participant count justifies it (§1.8, §1.10 in the FHIR doc's terms) — this is the only step that requires a new, neutral piece of shared infrastructure rather than a change any single party can make alone, and is explicitly **future work**, not part of the current reference implementation.

## Part 2 — Integrating NHID-Auth with OAuth2 and OpenID Connect

### 2.1 NHID-Auth is not a replacement for OAuth2/OIDC

NHID-Auth answers a narrower, healthcare-specific question than OAuth2/OIDC: *"Is this specific AI agent, on this specific call, authorized to act on behalf of this specific NPI-identified provider, right now?"* OAuth2/OIDC answer a different question: *"Is this software client allowed to call this API, and as which user/service identity?"* Both questions are usually live simultaneously in a real integration, and they should stay separate rather than be collapsed into one token.

### 2.2 How the two coexist

A typical vendor already uses OAuth2 (client credentials grant, most often) to call its own backend APIs, its EHR integration partner's APIs, or a payer's existing API gateway. None of that goes away. NHID-Auth sits *alongside* it as a call-scoped, cryptographically-signed object that travels with the call data — not instead of the bearer token that gets the request through the API gateway in the first place.

```
┌─────────────────────────────┐        ┌──────────────────────────────┐
│  OAuth2 access token         │        │  NHID-Auth AgentPassport      │
│  (client credentials grant)  │        │  (Delegation + signatures)    │
│  Proves: "this software      │        │  Proves: "this agent, on this │
│  client may call this API"   │        │  call, represents this NPI,   │
│                               │        │  within this scope"           │
└──────────────┬────────────────┘        └───────────────┬───────────────┘
               │                                          │
               ▼                                          ▼
        API Gateway / transport authorization      Call-level authorization,
        (who may connect at all)                   evaluated by the NHID
                                                     policy engine per call
```

### 2.3 Mapping NHID scopes to OAuth scopes

NHID delegation `scope` entries (e.g., `claims_inquiry`, `eligibility_check`) describe **what the agent is authorized to do on behalf of the provider**. OAuth scopes describe **what the API client is allowed to call**. They are related but not identical, and conflating them is a common integration mistake. Recommended mapping pattern:

| Layer | Example value | Lives in |
| :-- | :-- | :-- |
| OAuth scope | `nhid-api:calls:submit` | OAuth access token, checked by the API gateway before the request is even routed |
| NHID delegation scope | `claims_inquiry` | Inside the signed `Delegation` object, checked by the policy engine/verifier against what the call is actually trying to do |

A clean integration uses **one broad OAuth scope** ("this client may submit NHID-relevant call events at all") and lets the **NHID delegation scope do the fine-grained, per-provider, per-workflow authorization**. Do not try to mint a separate OAuth scope per provider NPI or per workflow — that's what the delegation object is for, and OAuth scope lists do not carry the cryptographic provider-signature guarantee a delegation does.

### 2.4 Representing NHID claims in JWTs or token introspection

If a deployment wants the convenience of carrying NHID context inside a JWT (e.g., so existing OAuth-aware middleware can read it without a separate parse step), the recommended pattern is a **private claim namespace**, not overloading standard claims:

```json
{
  "iss": "https://vendor.example.com/oauth",
  "sub": "client_beacon_runtime",
  "scope": "nhid-api:calls:submit",
  "https://nhid-clinical.org/claims/agent_id": "agent_beacon_001",
  "https://nhid-clinical.org/claims/provider_npi": "1234567890",
  "https://nhid-clinical.org/claims/delegation_id": "8f14e45f-...-uuid",
  "https://nhid-clinical.org/claims/call_sid": "CA123456789abc"
}
```

**Important caveat:** embedding these claims in the JWT is a *convenience copy* for downstream logging/routing, not the authorization itself. The actual authorization decision must still be made by verifying the underlying signed `Delegation`/`AgentPassport` object (whose signature these JWT claims merely restate) — never trust the JWT claim values for `provider_npi`/`delegation_id` without independently verifying the passport they were copied from, since a JWT issuer compromise would otherwise let an attacker forge claims without forging the underlying NHID signature.

**Embedded vs. referenced:** for short-lived, single-call tokens, embedding is fine. For longer-lived service tokens that span many calls, prefer a *reference* (just the `delegation_id`) and have the verifier fetch/verify the actual passport out of band — this avoids baking call-specific data into a token that outlives the call.

### 2.5 Client credentials for transport, NHID for behavioral/cryptographic guarantees

Standard pattern for service-to-service calls (e.g., the voice vendor's backend posting call events to a payer's NHID-aware webhook):

1. Vendor backend obtains an OAuth2 access token via client credentials grant against the payer's (or NHID gateway's) token endpoint — proves "this is a registered, authorized vendor backend."
2. Vendor backend includes the token as the standard `Authorization: Bearer` header.
3. The request body separately carries (or references) the `AgentPassport` for the specific call being reported.
4. The receiving service checks the OAuth token first (transport-level: is this caller allowed to talk to me at all), then independently verifies the passport (call-level: is this specific call's claimed authorization real).

Neither check substitutes for the other. A valid OAuth token with an invalid/missing passport should still result in the call being treated as non-conformant (e.g., `DENY_DATA` / IDG-01-equivalent failure) even though the *transport* request succeeded.

### 2.6 Avoiding confusion between client identity and caller authorization

The single most common integration error: treating "the OAuth client authenticated successfully" as equivalent to "this AI caller is authorized for this call." They are not the same fact. A vendor's backend service account can be perfectly validly authenticated via OAuth and still be reporting on a call where the *agent* had no valid provider delegation (e.g., delegation expired, wrong scope, revoked). Keep the checks architecturally separate in code — verify the OAuth token at the API/transport layer, verify the passport inside the policy-engine evaluation path — so that a future change to one doesn't silently weaken the other.

### 2.7 Provider-specific guidance: Auth0, Okta, Microsoft Entra ID, AWS Cognito, custom OIDC providers

None of these providers need to know anything about NHID-Auth — that's the point of keeping the layers separate. Integration guidance is the same shape for all of them:

- Use the provider's standard client-credentials (machine-to-machine) application type for the vendor backend's API access.
- Add the private NHID claim namespace (§2.4) as **custom claims** via whatever mechanism the provider supports (Auth0 Actions/Rules, Okta custom authorization server claims, Entra ID custom claims via a claims-mapping policy, Cognito pre-token-generation Lambda trigger) — these are convenience copies only, per the caveat in §2.4.
- Do not attempt to make the OIDC provider itself the verifier of NHID delegation signatures — none of these platforms have a concept of Ed25519 provider-delegation verification, and bolting that on via a custom claims-mapping function reintroduces the JWT-claim-trust problem from §2.4. Verification belongs in the NHID-aware application code (the policy engine / `AgentIdentityManager.verify_passport`), not the identity provider.

### 2.8 Short-lived tokens plus call-bound signed passports

This combination is the recommended steady state, not a transitional hack: OAuth2 access tokens should already be short-lived per standard OAuth2 hygiene (minutes to low hours), and NHID delegations should independently be bound to a call-SID with their own short TTL. The two expiries don't need to be synchronized — they're protecting against different threats (a leaked API token vs. a replayed call authorization).

### 2.9 Replay prevention when a bearer token spans multiple calls

This is precisely the gap NHID-Auth's call-SID nonce binding closes. An OAuth bearer token is, by design, valid for every request until it expires — it has no concept of "this specific call." If a vendor backend's OAuth token were the *only* authorization check, a leaked token (or a vendor bug that reuses a token across calls it shouldn't) could authorize an unbounded number of calls. The NHID delegation's `call_sid` field means even a leaked, still-valid OAuth token cannot be combined with a *replayed* passport from a different call — the verifier rejects the mismatch with `ERR_NONCE_MISMATCH`. This is the core answer to "why OAuth2 alone does not solve the NPI-bound, call-specific delegation problem": OAuth2 was never designed to express per-call scoping, and retrofitting it (e.g., minting a fresh OAuth token per call) is both non-standard and still wouldn't carry the provider's cryptographic signature over the NPI/scope/call binding the way a `Delegation` object does.

### 2.10 Reference integration patterns

**Tier 1 — Behavioral integration using OAuth2-protected API calls only.**
The vendor's backend authenticates to the NHID-aware API/webhook via OAuth2 client credentials. No agent keypairs, no delegations. Call transcripts/events are POSTed and evaluated against the behavioral controls (IDG-01/PDX-01/DBC-01/EIT-01/ATR-01) for a conformance verdict and CAS score. This is the integration tier most vendors should start at — see the [staged integration guide](v2-integration-guide.md), Tiers 0–1.

**Tier 2 — Full cryptographic integration: OAuth2 for transport, NHID-Auth for call-bound delegation.**
Same OAuth2 transport layer as Tier 1, plus: the provider has issued a signed `Delegation` to the vendor's agent keypair; every call event POST includes (or references) the corresponding `AgentPassport`; the receiving side runs `verify_passport` against the provider's known public key (via static exchange or JWKS, §1.8) before trusting the `provider_npi` the request claims to represent. See the [staged integration guide](v2-integration-guide.md), Tier 2, and §4.6 of the Master Knowledge Archive for the full code example.

**Future — OIDC-metadata or registry-based discovery (not yet implemented).**
An optional future model where a provider publishes an OIDC-style discovery document (or an entry in a shared NHID trust registry) that resolves NPI → current signing key/JWKS URL automatically, removing the need for bilateral static key exchange entirely. This depends on a registry operator existing (§1.8/§1.14) and is explicitly forward-looking — there is no reference implementation of this pattern in the current codebase.
