# NHID-Clinical Evidence Diagram System

**Status:** Normative for new visuals on nhid-clinical.org
**Version:** 1.0 · established 2026-09-05

This document exists because a visual audit of the eleven live destinations
found four coexisting visual systems, not one: a flat token-driven inline model
system, a generated/interactive layer, a "glossy 3D" external SVG set, and a
handful of one-offs including a third-party runtime dependency. Two of them
appeared on the same page.

It defines the one system new work uses, and the rules under which anything
gets published.

---

## 1. The governing principle

> **A visual is either a model, a reproducible evidence artifact, or a
> functional demonstration. It is never atmosphere.**

Three classes, and every visual on the site belongs to exactly one:

| Class | What it is | What it must carry | Examples |
| :--- | :--- | :--- | :--- |
| **Model** | A drawing of how something is structured or sequenced | A maturity classification stating it is conceptual, not measured | Interaction boundary, five-control model, disclosure-gate sequence |
| **Evidence artifact** | Generated by replaying repository data through real code | Source file, generator, verification command, version | Trust Gateway, enforcement ladder, shadow outcome chart, evidence scorecard |
| **Demonstration** | An interaction the reader can operate | Everything an evidence artifact carries, plus meaningful no-JS content | Front-desk walkthrough |

Anything that fits none of these does not get built. In particular: no
decorative gradients, no glow, no faux-dimensional stacks, no stock imagery of
hospitals, headsets, waveforms, circuits, padlocks or robots, no badge walls,
and no chart whose numbers are invented to make a shape.

**The line that matters most:** a model may never be presented as a
measurement. If a figure shows a workflow the framework *describes*, it carries
a `maturity-reference` or `maturity-conceptual` chip. If it shows what the
engine *returned*, it carries a provenance block. Never both, never neither.

## 2. Palette

Every colour comes from a CSS custom property defined in
`nhid-clinical-ui.css`. No new colour system, and no hardcoded hex in a figure.

| Token | Value | Role |
| :--- | :--- | :--- |
| `--ink` | `#0d2846` | Structural navy; headings, box titles |
| `--ink-soft` | `#1f2730` | Strong body text |
| `--body` | `#3a424b` | Body text, secondary labels |
| `--paper` | `#fdfcfa` | Figure ground |
| `--mist` | `#f6f4f0` | Recessed ground, provenance blocks |
| `--line` | `rgba(28,32,38,.14)` | Borders, connectors, arrowheads |
| `--teal` | `#14778f` | Control/gate accent, passes AA as text |
| `--teal-soft` | `#eaf3f1` | Gate fills |
| `--teal-bright` | `#14b8a6` | Interactive accent, "let through" |
| `--blue` | `#0b6ebc` | Audit/evidence accent, returns, dashed boundaries |
| `--blue-soft` | `#eef2f6` | Output-card fills |
| `--cyan` | `#67e8f9` | Illumination in the walkthrough scene only |

**Semantic use is fixed, not decorative:**

- Teal family — a control, a gate, something the framework enforces.
- Blue family — audit, evidence, a returned decision, a boundary that is
  observed rather than enforced. ATR-01 is always blue and always dashed.
- Two tones maximum in a chart, and both must mean something. The shadow
  outcome chart uses exactly two: what the engine let through, and what it
  would have acted on.

Brass (`#b79a62`) is authorised as a **material accent only**, on station
plaques inside the front-desk walkthrough. It is not a UI colour and does not
appear anywhere else.

### Dark mode is not optional

Style through tokens, never with a literal. A figure that names its own hex
cannot follow the theme toggle the site ships, which is why five of the site's
most prominent visuals ignored it. Inline SVG inherits `currentColor` and
custom properties automatically and is therefore the safe default; an external
`<img>` SVG cannot adapt at all and is the reason the glossy set is being
retired.

## 3. Typography

Three faces, already loaded by the site:

| Face | Use |
| :--- | :--- |
| **Raleway** 600–800 | Display headings only. Rare inside figures. |
| **Inter** 400–700 | Box titles, labels, explanatory text. |
| **IBM Plex Mono** 400–500 | Control IDs, reason codes, scenario IDs, counts, actions, commands, file paths. |

The monospace rule is load-bearing: anything a reader could paste into a
terminal or grep for in the repository is set in mono. `IDG-01`,
`IDG01_DISCLOSURE_CONFIRMED`, `nhid_ec_comp_001`, `evaluate_all`, `30/32` — all
mono. Prose describing them is not.

Sizes inside an 880-wide `viewBox`:

| Element | Size | Weight |
| :--- | ---: | :--- |
| Zone label (uppercase, tracked) | 9.5px | 400 |
| Verdict / count / reason code | 10–10.5px | 400–500 |
| Sub-label | 10.5px | 400 |
| Box title | 12.5px | 650 |
| Headline figure | 12.5px | 650 |

## 4. Geometry

**All primary models use `viewBox="0 0 880 H"`.** The width is fixed so that
figures share a type scale across pages; height varies with content. Existing
canonical heights: 320, 330, 380, 400, 430, 440.

- `width:100%; height:auto; display:block` on the SVG.
- The figure wrapper carries `overflow-x: auto` and the SVG a `min-width` in
  `rem` — below that the labels collide, so the figure scrolls inside its own
  box rather than shrinking into illegibility. This is deliberate: a diagram
  the reader must scroll is better than one they cannot read.
- 8px grid for box positions; 4px for internal padding.
- Corner radius 8–9px on primary boxes, 5–7px on secondary, 2–4px on chips.

**Connectors:** 1.5–1.8px stroke in `--line`, with a filled triangle
arrowhead (`<polygon>`, three points, 10px long × 10px wide). Flow left to
right and top to bottom. A dashed connector means an observed or returned
relationship; a solid one means a call or a transition.

**Reserved treatment:** ATR-01 is drawn `fill: none` with a dashed
`--blue` stroke wherever it appears, because it is not a gate. Any figure that
draws it as a fifth gate is wrong.

## 5. Accessibility contract

Every one of these is mandatory. A figure that misses any of them does not
ship.

```html
<figure class="…-model">
  <svg viewBox="0 0 880 H" role="img" aria-labelledby="x-title x-desc"
       style="width:100%;height:auto;display:block">
    <title id="x-title">A short name for the figure</title>
    <desc id="x-desc">The full content of the figure in prose, including
      every number and label a sighted reader can see.</desc>
    …
  </svg>
</figure>
```

- `role="img"` plus `aria-labelledby` pointing at both `<title>` and `<desc>`.
- `<desc>` states the figure's actual content, not its purpose. If a number is
  visible in the figure, it appears in the `<desc>`.
- **A complex figure also carries an adjacent prose form** — an ordered list, a
  table, or a paragraph — visible to everyone, not hidden. A concise `alt` or
  `desc` alone is not sufficient for a multi-step model. The disclosure-gate
  sequence carries a five-step ordered list; the evidence scorecard *is* a
  table.
- No meaning carried by colour alone. Every state that has a colour also has a
  word: `PASS`, `DENY_DATA`, `CHART SEALED`, a reason code.
- Keyboard: anything interactive is a real `<button>` with `aria-expanded`
  where it discloses, and a visible focus ring.
- Motion is decoration. Everything must honour `prefers-reduced-motion`, and
  no state may be reachable only through animation.
- **Nothing essential may depend on JavaScript to become visible.** Entrance
  animation is applied under `html.js`, set by the inline head script, so the
  default state without scripting is fully visible.

External SVGs referenced with `<img>`, where any remain, carry both a
meaningful `alt` and internal `<title>`/`<desc>`.

## 6. Provenance

Generated figures carry a `.visual-provenance` block naming four things:

```html
<aside class="visual-provenance">
  <p><strong>Evidence basis:</strong> <code>tests/evaluation_corpus_v1.json</code> — 25 scenarios, 55 turns</p>
  <p><strong>Generator:</strong> <code>scripts/build_evidence_visuals.py</code> ·
     <strong>Verification:</strong> <code>python scripts/build_evidence_visuals.py --check</code> (runs in CI)</p>
  <p><strong>Version:</strong> policy engine v1.3 · commit <code>abc1234</code></p>
</aside>
```

Conceptual figures instead carry a maturity chip and say plainly what they are:

> <span class="maturity-reference">Reference</span> Conceptual model of the
> control in a standard workflow. It is not a recording of a specific call.

**Raster and external assets** additionally record source, tool or author, date,
rights basis, and regeneration procedure. Where the tool is genuinely unknown,
the asset says `UNKNOWN` rather than implying provenance it does not have. An
asset whose origin cannot be established is a governance decision, not a design
one — see `trust-stack-3d.jpg`.

## 7. Generation rules

The Trust Gateway established the pattern and it is now the standard for any
figure that makes a factual claim:

```
repository data  →  replay through real code  →  generated figure  →  CI --check
```

Requirements for a generator:

1. **Read, never retype.** Reason codes are scraped from the engine source; the
   priority ladder is parsed from the engine's own mapping; published counts are
   read from their single definition with `ast.literal_eval`. A number typed
   into a generator is a second source of truth.
2. **Inject between sentinels.** `<!-- BEGIN GENERATED name -->` /
   `<!-- END GENERATED name -->`, so the guard can compare rendered markup, not
   just the data behind it.
3. **`--check` mode writes nothing and fails on drift**, and is wired into
   `.github/workflows/ci.yml`.
4. **Guard the invariants the data cannot express.** Choreography order,
   figure-specific rules, and "no hand-written verdict appears in the authored
   markup" belong in `--check`.
5. **Populations stay separate.** Four bodies of evidence measure four
   different things. Never combine them into one figure, one denominator, or
   one "accuracy" number.
6. **Say what is missing.** Where a fixture lacks a field a control reads, the
   figure states it. A low count that reflects an absent field is not a finding.

Note on tests: new pytest cases change the published unit-test count, which
`scripts/check_number_drift.py` propagates atomically across every surface that
prints it. Generator invariants therefore live in `--check` rather than in
`tests/`, which gives the same coverage at the same cadence without forcing an
unrelated count-propagation commit.

| `v2-identity-flow.svg` | No internal `<title>`/`<desc>` |
| `trust-stack-3d.jpg` | Provenance is a bare UUID and an unattributed signature — governance decision, not design |

Replacement is sequenced, not simultaneous. Nothing is deleted until its
replacement is published and a human has made a retention decision on the
original.
